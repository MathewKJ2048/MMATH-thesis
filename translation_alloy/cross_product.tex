Consider a simple field, as shown below:

\begin{lstlisting}
sig B, C {}
sig A {
	f : set B set -> set C
}
\end{lstlisting}

The field f is an element of $A \times B \times C$. In Alloy, Cartesian products are flat; $(A \times B) \times C$ is the same as $A \times (B \times C)$, which is also the same as $A \times B \times C$. In TLA+, Cartesian products are nested; $(A \times B) \times C$, $A \times (B \times C)$ and $A \times B \times C$ are distinct from each other, where $A \times B \times C$ corresponds to the flat product.

A simple implementation of a translation of Alloy's Cartesian product operator $(\rightarrow)$ is to use $A \times B \times C$ in TLA+. Since $A \times B \times C$ does not specify associativity, the result of the expression is a flat Cartesian product. However, this results in the following issues:

\begin{itemize}
	\item When translating an expression like $P \times (B \times C + A \times D)$, eliminating the brackets requires the translator to remake the whole expression by applying the distribution rule to get $P \times B \times C + P \times A \times D$. When predicates are introduced, this approach becomes intractable.
	\item When translating an expression such as $(A \times B)$, if the arity of A and B are not one, using the Cartesian product operator results in a non-flat set. The translator would have to compute the arity of A and B in the translation stage, and extract the inner components before applying the Cartesian product operator. 
\end{itemize}

An alternative method to represent Cartesian products exploits the fact that in TLA+, a tuple is treated the same as a list. Using this fact, a macro for Cartesian products that treats tuples as lists, is used in place of the Alloy Cartesian product operator.

When we treat tuples as lists, the above model is translated as:

\begin{lstlisting}
_cross(A,B) == A \o B
\\ A and B are lists, which are concatenated
f \in _cross(A,_cross(B,C))
\end{lstlisting}

With this representation, the associativity of the macro is irrelevant, since the end result is the same whether the application is left or right associative. This matches the semantics of the Cartesian product in Alloy.

As a consequence, the representation of signatures changes, from sets of strings, to sets of tuples of arity one (or lists of length 1). This is necessary, since TLA+ does not allow dynamic type-checking to determine whether a macro is applied on a string or a tuple. By representing signatures as tuples/lists, a single macro covers all the cases where a Cartesian product is applied:

\begin{itemize}
	\item signature cross signature
	\item signature cross field
	\item field cross signature
	\item field cross field
\end{itemize}

\begin{lstlisting}
sig B, C {}
\end{lstlisting}

is translated as:

\begin{lstlisting}
B \in {<<"B0">>,<<"B1">>,<<"B2">>}
/\ C \in {<<"C0">>,<<"C1">>,<<"C2">>}
\end{lstlisting}
